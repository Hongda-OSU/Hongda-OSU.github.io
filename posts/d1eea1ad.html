TAG 工作总结

发表于2025-02-26|更新于2026-11-15|工作
|字数总计:2k|阅读时长:6分钟

我在 TAG（The Aspen Group，一家大型牙科医疗集团，旗下 Aspen Dental 有 1400 多家门店）做了一年半的后端开发，这篇是这段工作的小结：我负责什么、用了哪些技术、自己主导了哪两个项目，以及学到的东西。

我在 TAG 的职责

  • 负责 Clinical 相关微服务的开发和维护。公司的门店系统是自研的，需要持续维护和迭代

    • 采用 Model-Service-Repository 模式组织代码，提高可维护性
    • 日常维护多个 .NET 微服务，修复 bug，开发新的业务功能

  • 负责 Monolith（同样是 .NET）的维护和 bug 修复

    • 阅读和理解遗留代码，定位并修复问题
    • 把 Clinical 相关的功能从 Monolith 拆分到微服务

  • 数据库相关工作

    • Monolith 用 SQL Server，微服务用 PostgreSQL
    • 根据 PM 的需求开发新功能，或者调整数据

  • 跨团队协作

    • 帮后端队友做 Code Review（我是团队里唯一的非 Senior）
    • 解答前端队友的后端问题，协助前后端联调
    • 帮 PM 做技术调研（SPIKE）
    • 需要时支援其他 team

我在 TAG 的技术栈

  • Frontend： 能读懂 Angular 和 React（微前端）
  • Backend： C#、.NET 6 到 9（Monolith 是 .NET 6，其他微服务基本都是 .NET 9）、GraphQL（公司有一层 GraphQL，不过我个人更喜欢直接的 REST）、gRPC
  • Database： PostgreSQL、SQL Server、AlloyDB、Firestore
  • ORM： Dapper、Entity Framework（微服务主要用 Dapper，Monolith 用 Entity Framework）
  • Cloud： GCP（Pub/Sub、AlloyDB、DMS、BigQuery）
  • DevOps： Docker、Kubernetes、Terraform、Spinnaker、Liquibase
  • Monitoring： Grafana
  • Other Tools： LaunchDarkly、NuGet、Git、GitHub

我主导的项目

除了日常维护组里的微服务，我也独立主导了两个项目。

TAG Notifications

问题：诊所需要在患者到店时，根据过往的治疗记录提醒做复诊检查（recall exam）。这既能提升服务质量，也能带来营收，但当时没有一个统一的服务来管理这些提醒。

做法：从数据库设计到微服务开发都由我独立完成。整体的数据流如下：

1. 数据库设计

数据存在 AlloyDB（兼容 PostgreSQL）里，用 Liquibase 管理 schema 变更。schema 由我独立设计，和 Senior、Tech Lead 讨论过好几轮才定下来。微服务和 Cron Job 都完成后，再根据实际的查询来设计索引。

2. Nightly Cron Job（定时任务）

Cron Job 负责两件事：

  • 初始化数据： 从 Monolith 读取需要的数据，生成对应的 notification
  • 每日增量同步： 每天晚上根据 checkpoint 从 Monolith 同步变化的数据。Monolith 是数据的 source of truth，所以要保证两边一致

Monolith 的数据量在千万级别，所以我用了几种优化：

  • 分批读取： 数据没法一次读完，按批次分页读取
  • 并行写入： 设置并发的 worker，每读完一批，就交给空闲的线程去做 bulk upsert，主流程不用等 upsert 完成，直接读下一批
  • 任务并行： 互不依赖的任务同时运行

优化后，处理 10 万条数据只需要 10 秒左右。

3. Notification Subscriber（发布-订阅）

  • Subscriber 是一个独立的 Worker，专门消费 GCP Pub/Sub 的订阅，监听 Monolith 和其他 team 发来的事件并实时更新数据库，保证白天用户看到的数据是最新的
  • 之所以没有把 Subscriber 放进微服务里，是因为它要处理的消息量很大、并发很高（在类似 Visit Manager 的页面里被使用）。如果放在微服务里，流量一上来就得把整个微服务扩容，并不合理。单独拆出来可以独立扩容，两边也解耦了

技术要点：

  • 用 Terraform 创建 GCP 的 subscription 和 dead letter queue
  • 梳理需要监听哪些事件，为不同的事件写了不同的 message handler
  • 沿用 Cron Job 里的优化：互不依赖的任务同时运行
  • 用 Redis 缓存静态数据，减少数据库查询

4. Notification MS（微服务）

一个标准的 .NET 9 微服务，给前端、GraphQL team 和其他微服务提供所需的 API。

结果：这个服务在设计时就考虑了扩展性，现在不只我们 Clinical team 在用，其他 team 也依赖它，并提出自己的 notification 需求，不同的品牌也可以定制自己的规则。这是我做过最大的一个项目，目前还在持续完善。

通过这个项目，我学到了：

  • 数据库设计和 PostgreSQL 的使用
  • 并行编程和 Cron Job 开发（用 GCP Log Explorer 加 Stopwatch 测速度）
  • GCP Pub/Sub 的使用和不同消息的处理
  • 怎么把 PM 比较宽泛的需求落地成具体的技术方案：Notification 的概念很简单，实现起来却很复杂

TAG Feature Flag（LaunchDarkly）

问题：我负责的一部分工作是试点项目（pilot project），也就是新功能先在一部分门店里试用。原来控制试点用的是 Monolith 数据库里专门的 pilot project 表和 pilot facility 表，但 Monolith 的数据库不能随时发布，要等每周固定的发布时间，所以新的试点项目往往要等到下周才能上线。

正好那时前端刚开始用 LaunchDarkly 做 feature flag，我的 manager 就让我调研后端怎么用 LaunchDarkly 来控制试点。

做法：设计并实现了一个 Feature Flag 的 NuGet 包，分成两部分：

  • Abstraction 包： 定义统一的接口，避免和某个厂商绑死。将来如果从 LaunchDarkly 换成别的 feature flag 产品，只要重新实现这套接口就行
  • Implementation 包： 基于 LaunchDarkly 实现，用工厂模式加延迟初始化 client 来优化性能

结果：这个包被多个 team 采用，覆盖全国 2000 多家门店。各 team 可以自己管理和上线试点项目，不用再等数据库发布。现在还和 Metric team 合作，可以在他们那边看到每个试点项目的采用率。

通过这个项目，我学会了怎么写 NuGet 包（类似 npm 包），以及怎么设计低耦合的软件

我学到的东西

如何设计微服务

我们 Clinical team 用 Model-Service-Repository 模式构建 C# 微服务，提升代码的可维护性和扩展性：

  • Model： 定义数据结构，比如 Request 和 Response 的结构
  • Repository： 负责数据库操作，封装 SQL 查询，对外提供数据访问接口（用 Dapper 写和数据库交互的逻辑）
  • Service： 负责核心业务逻辑，调用 Repository 读取和修改数据

Repository 和 Service 都要建对应的 Interface，用来定义方法签名，并写注释说明方法的用途。

如何使用 IaC（Terraform）

之前团队都是在 GCP Console 里手动创建资源，不好管理，也很难追溯改动。我自己学了 Terraform，在不占用 DevOps 人力的情况下：

  • 创建 Pub/Sub 的 subscription 和 dead letter queue
  • 写了 GCP DMS 的模板，用于数据迁移

之前团队用 SSIS 把数据从 Monolith 的 SQL Server 迁移到 AlloyDB，流程很复杂，懂的人也不多。所以我在写 Pub/Sub 模板的同时，研究了 GCP DMS（Database Migration Service），基于 Terraform 提供的 DMS 模板做了一套组合，让其他 team 也能更方便地做数据迁移。

如何提高 API 性能

在 Aspen，我们用两种方式衡量 API 性能：用 Grafana 监控响应时间等指标，以及做压力测试，了解 API 在高负载下的表现。

优化方面主要是三件事：优化 SQL 查询、用缓存（比如 Redis 缓存静态数据）、和 Senior 一起 Code Review 讨论 API 设计。

如何从零开始做东西

不管是做微服务还是 NuGet 包，最重要的是先做出一个模板，让别人能复用。这样后续的项目可以基于模板快速开始，不用每次都从头配置。
